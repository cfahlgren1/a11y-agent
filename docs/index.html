How I built a11y-agent

Turning the take-home's starter_agent.py into an accessibility & layout audit agent that drives a real browser, discovers pages with Tavily Map, and writes an evidence-backed report — then audits Tavily's own dashboard with it.

Context: why this page exists (there is no chat log)

The take-home asks for "a record of how you built this." The build happened in one Claude Code session — but its transcript was never saved: the terminal had inherited an internal CLAUDE_CODE_CHILD_SESSION env marker that silently turns transcript saving off. Diagnosed post-hoc by walking the marker up the process tree, PID by PID. This page is the honest substitute: a forensic reconstruction from everything that did survive.

WHY THE TRANSCRIPT WENT AWAY

  earlier Claude Code session
  │  exports CLAUDE_CODE_CHILD_SESSION=1 into its child processes
  │  (so nested claude runs don't save duplicate transcripts)
  │
  └─▶ ran `cursor .` from inside that session
      │
      └─▶ Cursor (new instance)
          │  inherits the whole environment, marker included,
          │  and keeps it for its entire lifetime
          │
          └─▶ Cursor integrated terminal (zsh)
              │  inherits it again — nothing in .zshrc sets or clears it
              │
              └─▶ `claude` (the build session)
                     sees CLAUDE_CODE_CHILD_SESSION=1
                     → "I must be a nested child session"
                     → no .jsonl written, silently
                       (warning banner only added in v2.1.217+)

  What still got written, marker or not:
    ✓ subagent metadata        ✓ file-history snapshots
    ✓ saved tool results       ✓ git commits
    ✓ results/report.md + screenshots
  …which is exactly what this reconstruction is built from.

Build process

Six phases in one session. Research fanned out to parallel subagents before any code was written; an independent Codex review and throwaway probe scripts kept the middle honest; the session ended by running the finished agent against Tavily's own logged-in dashboard.

Saving the report

The plan originally said "no saved-report machinery" — the audit would just stream to the terminal. Once a durable artifact mattered, the question became how much filesystem access the agent should get. I drafted both options before deciding (the abandoned draft survives as a 13:18 file-history snapshot):

General read / edit / write toolsSingle save_report tool (shipped)
CapabilityAgent can read files back, iterate on drafts, manage multiple artifacts — confined to allowed rootsWrites exactly one file: report.md into the run's output dir. No path argument at all
Blast radiusThis agent reads untrusted web pages. Codex's High finding: prompt-injection on an audited page could steer any write-capable tool. Path confinement helps, but it's more code to get rightA malicious page can at worst overwrite the report. Nothing else is reachable
Scope fitMore surface to build, test, and harden inside a 4–6h take-home31 lines (report.py), trivially reviewable

For the scope of this project the blast radius wasn't worth it — the simple tool won. Screenshots don't need a write tool at all: AGENT_BROWSER_SCREENSHOT_DIR redirects them into the same output dir (verified by the 13:10 probes), and the report references them by bare filename. The SKILL.md's Output section tells the agent to finish every audit with save_report.
